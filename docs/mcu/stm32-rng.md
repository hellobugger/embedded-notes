# STM32 RNG 硬件随机数生成器：从熵源到安全使用的一篇讲透

> 一句话：**RNG 外设把芯片内部的物理噪声变成随机比特，再由硬件输出 32 位随机数**。要用对它，必须先分清三件事——**随机性从哪里来**、**硬件什么时候真的准备好一个数**、**随机数到底拿来做什么**。本文以 STM32F4 的经典 RNG 为主，同时说明 F2/F7/H7/L4/G4 等系列在时钟、错误标志和 HAL 接口上的差异。

## 一、RNG 是什么，和 `rand()` 有什么区别

RNG（Random Number Generator，随机数生成器）是 MCU 内部的专用硬件外设。它不是根据一个固定种子计算序列，而是利用芯片内部噪声源产生熵，再经过数字电路整理后输出随机数据。

```text
内部模拟噪声源 ─→ 随机性处理/健康检测 ─→ 32 位数据寄存器 ─→ CPU / DMA
                         │
                         └─错误标志：时钟错误、种子错误等
```

需要把三个概念分开：

| 名称 | 本质 | 能否预测 | 适用场景 |
| ---- | ---- | -------- | -------- |
| `rand()` | 软件伪随机算法 | 知道种子后通常可预测 | 仿真、界面、非安全随机 |
| LFSR/LCG | 软件或硬件伪随机序列 | 周期和状态可分析 | 测试序列、扰动、快速模拟 |
| **STM32 RNG** | 物理噪声驱动的硬件随机源 | 设计目标是不可预测 | 密钥种子、Nonce、挑战值、随机抖动 |

RNG 适合提供**熵**，但“有 RNG”不等于“自动完成了密码学系统”。密钥生命周期、密钥存储、协议 Nonce 不能重复、失败时如何停机，仍然需要应用层负责。

!!! warning "先确认型号是否真的有 RNG"
    STM32 不同子系列的 RNG 配置完全不统一：F1/F3 的很多型号没有 RNG，F4 部分型号有，F0/G0/L0 的部分型号也可能没有；H5/U5 等新系列还可能增加健康测试和更严格的安全特性。**先查具体型号的数据手册和参考手册的 RNG 章节，再复制代码。**

## 二、硬件内部做了什么

### 2.1 随机数从哪里来

RNG 的输入不是系统时钟计数值，也不是 ADC 采样值，而是芯片内部专门设计的噪声源。常见实现会利用振荡器抖动、热噪声等物理不确定性，再由数字逻辑组合和采样，形成随机比特流。

工程上应该把它理解成：

1. 模拟噪声提供不可预测的原始熵；
2. 数字电路把原始比特整理成固定宽度输出；
3. 健康检测发现时钟或熵源异常时置错误标志；
4. 软件只在数据就绪时读取数据寄存器。

这个过程不是“读取一个会变化的寄存器”。如果 RNG 时钟没开、外设没使能，读取 `DR` 可能得到旧值、固定值或无效状态。

### 2.2 32 位输出不等于每一位都独立

经典 STM32 RNG 以 32 位为单位输出数据。一个 32 位字通常可以作为随机种子、会话随机数或协议字段使用，但不能只凭“32 位”三个字判断密码学质量。真正的随机性取决于：

- 具体系列使用的 RNG 设计；
- 时钟是否稳定且满足手册要求；
- RNG 是否报告时钟/种子错误；
- 是否按推荐流程处理连续输出；
- 系统是否经过实际健康监测和故障处理。

如果用途是密钥、认证挑战、令牌或安全协议，优先使用 STM32Cube 对应系列提供的官方 HAL/LL，并结合安全库的随机数回调；不要为了省几行代码直接绕过错误检查。

## 三、时钟、复位与数据路径

### 3.1 RNG 时钟不是系统时钟的“顺便使用”

以 F4 为例，RNG 通常挂在 AHB2，时钟由 RCC 单独控制。典型初始化顺序是：

```text
系统时钟稳定
   ↓
开启 RNG 外设时钟
   ↓
配置 RNG 时钟源/分频（若该系列提供）
   ↓
释放复位（如需要）
   ↓
使能 RNG
   ↓
等待 DRDY，再读取 DR
```

F4 经典型号一般通过 `__HAL_RCC_RNG_CLK_ENABLE()` 开启时钟，RNG 时钟来自指定的 48 MHz 时钟域，具体来源和约束要看型号。较新系列可能使用独立的 RNG 时钟选择器、PLL48、HSI48 或内核时钟分频。

!!! warning "RNG 时钟过高或不稳定会直接影响可靠性"
    RNG 的时钟频率通常有手册规定范围。时钟太低会降低吞吐量，时钟超规格或 48 MHz 时钟域配置错误，可能触发 `CECS` 时钟错误。不要只看到“RNG 已勾选”就忽略时钟树。

### 3.2 外设数据通路

经典 RNG 的核心寄存器可以抽象为：

| 寄存器/标志 | 作用 |
| ----------- | ---- |
| `CR` | 使能 RNG；某些系列还包含中断/DMA控制位 |
| `SR` | 读取数据就绪、时钟错误、种子错误等状态 |
| `DR` | 读取最新的 32 位随机数 |
| `DRDY` | `DR` 中已有可读数据 |
| `CECS/SECS` | 时钟错误/种子错误状态，命名随系列略有差异 |

典型工作过程：

```text
RNG 运行 → 产生 32 位字 → DRDY=1 → 软件/ DMA 读取 DR → DRDY 清除 → 继续产生下一个字
```

**读取 `DR` 是消费动作**。因此不能在多个任务里无保护地同时调用底层读寄存器；应由一个随机数服务统一读取，或使用互斥锁保护 HAL 接口。

## 四、CubeMX 配置：逐项看懂每个选项

1. 在 `System Core / Connectivity` 中启用 `RNG`；不同系列的位置可能不同。
2. 在 RCC/时钟配置页确认 RNG 需要的 48 MHz 时钟域已经正常输出。
3. 生成代码后检查 `HAL_RNG_MspInit()` 是否开启了 RNG 时钟。
4. 若使用中断或 DMA，确认对应 NVIC/DMA 请求映射，而不要只看外设页面。
5. 把随机数读取封装到自己的模块里，应用代码不要到处直接访问 `hrng`。

F4 常见生成代码结构如下：

```c
RNG_HandleTypeDef hrng;

void MX_RNG_Init(void)
{
    hrng.Instance = RNG;
    if (HAL_RNG_Init(&hrng) != HAL_OK) {
        Error_Handler();
    }
}
```

`HAL_RNG_Init()` 负责初始化外设句柄和底层配置；真正取数还要调用 `HAL_RNG_GenerateRandomNumber()`。

## 五、HAL 取数：轮询、中断与 DMA

### 5.1 轮询：默认且最容易验证

```c
uint32_t random_word;

if (HAL_RNG_GenerateRandomNumber(&hrng, &random_word) != HAL_OK) {
    /* 记录 hrng.ErrorCode；安全场景下不要继续生成密钥 */
    Error_Handler();
}
```

经典 HAL 接口会等待 `DRDY`，然后检查错误状态并读取 `DR`。超时值和错误码由 HAL 版本决定；如果项目要求任务不能长时间阻塞，使用带超时的扩展接口（若当前系列 HAL 提供）或改用中断/DMA。

### 5.2 连续读取与批量填充

```c
static int rng_fill(uint32_t *buf, size_t words)
{
    for (size_t i = 0; i < words; ++i) {
        if (HAL_RNG_GenerateRandomNumber(&hrng, &buf[i]) != HAL_OK) {
            return -1;
        }
    }
    return 0;
}
```

这个包装的价值不只是省代码：它可以统一处理错误、统计失败次数、加锁，并把“随机源不可用”传递给上层。

### 5.3 中断与 DMA：吞吐量优先时再用

部分系列和 HAL 支持 `HAL_RNG_GenerateRandomNumber_IT()`、`HAL_RNG_GenerateRandomNumber_DMA()`。典型流程是先准备缓冲区，再启动读取，数据完成后由回调通知应用：

```c
static uint32_t entropy_buf[32];

HAL_RNG_GenerateRandomNumber_DMA(&hrng, entropy_buf, 32);

void HAL_RNG_ReadyDataCallback(RNG_HandleTypeDef *hrng)
{
    /* 只做置标志/投递消息；不要在回调里执行耗时密码运算 */
    entropy_ready = 1;
}
```

具体函数名和回调名随 Cube HAL 版本/系列可能不同，生成后以对应 `stm32xxxx_hal_rng.h` 为准。DMA 适合一次填充较大熵池，偶尔取一个随机数仍优先用轮询，调试和错误处理更直观。

## 六、错误处理：随机源出错时不能“凑一个数”

经典 RNG 至少要关注两类故障：

- **时钟错误**：RNG 时钟不在允许范围、时钟源异常或时钟检测失败；
- **种子错误**：内部噪声源或健康检测发现异常，不能认为当前数据可信。

```c
uint32_t r;
if (HAL_RNG_GenerateRandomNumber(&hrng, &r) != HAL_OK) {
    uint32_t err = HAL_RNG_GetError(&hrng);
    /* 记录 err，停用当前安全操作，按产品策略复位或报警 */
}
```

错误处理建议按用途分级：

| 用途 | RNG 出错后的处理 |
| ---- | ---------------- |
| UI 动画、测试数据 | 可记录并切换到明确标记的伪随机源 |
| 网络会话 Nonce | 终止本次会话，重新初始化或上报故障 |
| 密钥生成/安全启动 | **禁止回退到 `rand()`**，进入安全失败路径 |
| 生产测试 | 保存错误计数、时钟配置和复位原因，便于定位硬件问题 |

!!! warning "不要用固定值掩盖 RNG 故障"
    `HAL_RNG_GenerateRandomNumber()` 失败后，如果代码继续使用未初始化的变量、上一次随机数或固定默认值，安全意义会完全改变。随机数获取函数必须返回成功/失败，调用者必须检查结果。

## 七、随机数如何进入实际应用

### 7.1 生成安全长度的缓冲区

```c
#include <stdint.h>
#include <stddef.h>

int secure_random_bytes(uint8_t *out, size_t len)
{
    while (len != 0U) {
        uint32_t word;
        if (HAL_RNG_GenerateRandomNumber(&hrng, &word) != HAL_OK) {
            return -1;
        }

        size_t n = (len < sizeof(word)) ? len : sizeof(word);
        for (size_t i = 0; i < n; ++i) {
            out[i] = (uint8_t)(word >> (8U * i));
        }
        out += n;
        len -= n;
    }
    return 0;
}
```

该示例采用小端方式拆字节。协议若规定网络字节序，应在协议编码层使用明确的大小端转换；随机性本身不依赖字节顺序，但对端解析依赖。

### 7.2 生成范围内的整数：避免取模偏差

直接写 `r % n` 可能产生偏差，因为 `2^32` 不一定是 `n` 的整数倍。需要无偏整数时使用拒绝采样：

```c
int random_below(uint32_t limit, uint32_t *value)
{
    if (limit == 0U || value == NULL) {
        return -1;
    }

    uint32_t threshold = (uint32_t)(-limit % limit);
    for (;;) {
        uint32_t r;
        if (HAL_RNG_GenerateRandomNumber(&hrng, &r) != HAL_OK) {
            return -1;
        }
        if (r >= threshold) {
            *value = r % limit;
            return 0;
        }
    }
}
```

### 7.3 作为密码库的熵源

TLS、AES-CTR/DRBG、椭圆曲线密钥生成等安全库通常需要随机数回调。应让回调：

- 能报告硬件 RNG 失败；
- 不能返回未初始化数据；
- 不能在中断上下文阻塞；
- 必要时加互斥锁；
- 在低功耗和时钟切换后确认 RNG 仍可用。

RNG 只负责提供熵，密钥是否长期保密还要看 Flash 读保护、TrustZone、调试口和密钥擦除策略。

## 八、低功耗、复位与 RTOS 注意事项

- 进入 STOP/低功耗前，RNG 通常会停止；唤醒后要确认 RNG 时钟已经恢复，再重新使能或重新初始化。
- 系统时钟切换后，若 RNG 依赖 PLL48/HSI48，必须重新检查时钟树和 `RNG_SR` 错误标志。
- RNG 外设复位会清除内部状态；不要在一个任务正在读取时从另一个任务复位 RNG。
- RTOS 下建议建立单一 `entropy_task` 或随机服务，其他任务通过队列/接口取数；至少用互斥锁保护 HAL 句柄。
- 不要在高优先级中断里轮询等待 RNG；中断里只投递请求或使用提前填好的熵池。

## 九、验证与测试

功能验证可以做以下检查：

1. 连续读取几千个 32 位字，确认不会长期固定或重复；
2. 故意关闭 RNG 时钟，确认上层能收到失败而不是继续使用数据；
3. 改变系统时钟配置，确认 RNG 仍满足手册范围；
4. 低功耗唤醒后再次取数，确认初始化顺序正确；
5. 在 RTOS 下多任务并发调用，确认没有数据竞争。

统计频数、游程和重复率只能发现明显故障，**不能证明随机数满足密码学要求**。需要正式评估时，应依据具体器件安全手册、应用标准和实验室测试流程。

## 十、常见坑汇总

- **把 `rand()` 当硬件 RNG**：两者不是一回事，`srand(HAL_GetTick())` 不能用于密钥。
- **没开 RNG 时钟就读 `DR`**：先检查 RCC 和 RNG 使能。
- **忽略 `HAL` 返回值**：错误时不能继续使用输出变量。
- **RNG 时钟超规格**：优先检查 PLL48/HSI48 和系列时钟选择器。
- **多任务同时取数**：`DR` 是消费型寄存器，给随机服务加锁。
- **低功耗唤醒后直接取数**：先恢复时钟，再重新初始化或清除错误状态。
- **`r % n` 生成范围数**：对安全用途会产生模偏差，使用拒绝采样。
- **误以为 RNG 自动保护密钥**：密钥存储、擦除和调试口保护仍需单独设计。
