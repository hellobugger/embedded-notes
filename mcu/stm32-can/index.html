    CAN 总线：从通信机制到收发中断的一篇讲透

    一句话：CAN 是一根差分双绞线上的「多人会议室」——任何人想说话就抢总线，抢到了就广播，谁需要谁收；不许吵架（协议层自动仲裁）、说错话会被纠正（错误帧隔离）、甚至有人摔门离开会被请回来（Bus-Off 快慢恢复）。要讲清楚的其实是七件事——它凭什么在一根线上多人通信（通信机制）、消息长什么样（数据帧）、怎么保证不错（错误检测）、怎么对表（位定时与同步）、工程上怎么配（配置说明）、收发中断怎么用、以及出了大事故怎么自救（Bus-Off 快慢恢复）。本文以 STM32 bxCAN（F1/F4）为主，寄存器名与配置以 HAL 为准。

    一、通信机制：为什么一根线上能挂一堆人

    CAN 是 多主 + 广播 + 仲裁 的总线，这三点决定了它的性格。

    多主：总线上没有「主机」，任何节点都能主动发起发送，谁想发谁抢。

    广播：节点发送的消息不指定「发给谁」，所有人都能听到。谁需要，靠验收过滤器（见配置节）留下自己关心的 ID，其余丢弃。

    仲裁（防碰撞）：两个节点同时发时，靠 ID 小的优先 自动裁决，赢的继续发，输的自动退让并转为接收。这件事在位电平上硬件自动完成，应用层无感知——这是 CAN 和 RS-485（半双工一问一答）最大的区别：CAN 不需要主从轮询，天然适合 ECU 之间互相喊话。

    一句话理解仲裁：显性位（逻辑 0）永远压过隐性位（逻辑 1）。谁先输出 0，谁就赢了。所以 ID 越小优先级越高，0x000 永远是最牛的车。

    两条线、两个电平：CAN_H / CAN_L 差分传输，有两种逻辑状态：

    状态 CAN_H CAN_L 差压 说明
    显性 Dominant 约 3.5V 约 1.5V ≈2V 逻辑 0，仲裁时赢
    隐性 Recessive 约 2.5V 约 2.5V ≈0V 逻辑 1，仲裁时输

    每个节点都要接终端电阻（120Ω），挂在总线两端各一个，用来匹配阻抗、抑制信号反射。缺终端电阻，高速率下波形畸变，通信时好时坏，这是 CAN 调试最经典的坑。

    二、数据帧：消息长什么样

    CAN 的消息单元叫帧，常见三种：数据帧（带数据）、远程帧（只问不带数据，RTR=1）、错误帧（出错时冲掉总线）。日常 99% 用的是数据帧。数据帧分标准帧和扩展帧，区别只在一个 ID 字段：

    帧类型 标识符 格式位 数据 一帧最多位
    标准帧 11 位 ID（0x000~0x7FF） IDE=0 0~8 字节 约 108 位
    扩展帧 29 位 ID（0x00000000~0x1FFFFFFF） IDE=1 0~8 字节 约 128 位

    标准帧结构（逐字段拆解）

     起始位  仲裁场(12位)        控制场(6位)             数据场(0~8B)   CRC场(16位)    ACK场     EOF
 ┌────┐ ┌────────────────┐ ┌────────────────────┐ ┌────────────┐ ┌─────────────┐ ┌────────┐ ┌────┐
 │ SOF │ │ ID(11位) + RTR │ │ IDE + r0 + DLC(4位) │ │  Data...   │ │ CRC(15) + DEL │ │  ACK   │ │ 7个 │
 └────┘ └────────────────┘ └────────────────────┘ └────────────┘ └─────────────┘ └────────┘ └────┘
  1bit      11bit + 1bit          1 + 1 + 4bit           0~64bit         15 + 1bit      1+1bit     1bit
    字段 长度 作用
    SOF 1 位 起始位，显性 0，标志帧开始
    ID 11 / 29 位 标识符，越小优先级越高；也是接收方过滤的依据
    RTR 1 位 远程帧标志：0=数据帧，1=远程帧
    IDE 1 位 扩展标志：0=标准帧，1=扩展帧
    r0 1 位 保留位
    DLC 4 位 数据长度，0~8（高 4 位为 r1 扩展位）
    数据 0~8 字节 载荷，最多 8 字节（CAN FD 可到 64 字节）
    CRC 15 位 + 1 分隔位 校验数据，出错接收方拒收并报错
    ACK 2 位（ACK 槽 + 分隔位） 发送方发隐性 1；只要有节点正确收到就把它拉成显性 0。发送方在 ACK 槽读到 0 = 有人收到了；读到 1 = 总线上没别人（只有一个节点，没对表对象）
    EOF 7 位 结束标志，7 个隐性位

    位填充（Bit Stuffing）——不占字段的「隐形防错」

    从 SOF 到 CRC 结束，连续出现 5 个相同位就自动插入 1 个相反位。作用有二：

    • 提供沿沿：接收方靠电平跳变同步时钟，一连串长 0/长 1 会让接收方失去采样点，填充位保证总线最多 5 位就有一次跳变；
    • 错误检测：接收方如果读到连续 6 个相同位，说明破坏了规则 → 立刻报错（位填充错误）。

    EOF 和后面的帧间空间不参与填充。这条规则也让一个有趣的工程结论成立：把 CAN 报文里填充 0xFF 或 0x00 的「空数据」容易触发位填充，网络空闲时段总线反而不安静——这是干扰排查时的一个冷门知识点。

    三、错误检测：CAN 凭什么敢说「几乎不会错」

    CAN 的错误检测是五层防护，这是它敢用在汽车刹车、动力系统上的底气：

    检测层 检测什么 谁发现
    位填充错误 连续 6 个相同位 所有接收方
    CRC 校验 数据完整性 所有接收方
    位错误 发送方发送和监听的电平不一致（被干扰/被抢线） 发送方自己
    应答错误 ACK 槽收不到隐性位的确认 发送方自己（总线上没别人）
    格式错误 固定位（r0/r1、CRC 分隔位、EOF 等）不为预期值 所有接收方

    任一层出错，节点就进入错误状态并发送错误帧（主动错误帧=6 个显性位，冲掉当前总线上的半个坏帧；被动错误帧=6 个隐性位，不干扰别人）。出错方会重发，前提是总线还抢得到。

    关键点：CAN 的可靠性不是「不犯错」，而是「错了一定被大家发现、且被错误帧标记」。5 层检测 + 错误帧广播，误帧率低到可以用于安全关键场合。

    节点按错误计数（TEC 发送计数 / REC 接收计数）分成三个状态，这就是 Bus-Off 恢复的话题了（见第六节）：

    状态 计数范围 行为 正常接收/发送
    错误主动（Error-Active） TEC/REC < 128 正常收发；出错时发主动错误帧（显性 6 位，能把别人的坏帧冲掉） ✅
    错误被动（Error-Passive） 128 ≤ 任一 < 256 还能收发，但出错只发被动错误帧（隐性 6 位），且发完必须等 8 个隐性位才可再发（被「限速」了） ⚠️ 受限制
    Bus-Off TEC ≥ 256 完全退出总线，既不收也不发 ❌

    四、位定时与同步：接收方怎么「对表」采样

    CAN 是异步总线——没有独立的时钟线，接收方要从总线的电平跳变里自己恢复时钟。这就是位定时与同步要解决的「对表」问题。波特率相同是不够的，节点间的时钟漂移（晶振误差）由同步机制吸收。

    一位被切成多少份：TQ

    每一位（bit time）被细分成最小时间单元 TQ（Time Quantum），波特率只由 TQ 数决定，每个 CAN 控制器的 TQ 划分不同，这就是为什么同一条总线上所有节点的波特率必须一致。F1/F4 的 bxCAN 中 TQ 由 APB1 时钟分频而来：

    TQ = (BRP + 1) / APB1_CLK        // BRP 波特率预分频器
1 bit  = 1 × SYNC_SEG + BS1 + BS2  // 典型 8~25 个 TQ
波特率 = APB1_CLK / (BRP+1) / (1 + BS1 + BS2)

    每个位分为 4 段，三段组合成一个采样点：

    段 作用 典型 TQ
    SYNC_SEG 同步段，固定 1 TQ，沿必须落在这里 1
    BS1（传播段 + 相位段1） 吸收总线传播延迟 + 允许相位调整 4~8
    BS2（相位段2） 采样点之后的部分，允许相位调整 2~6 
            |<-- 1 bit = N 个 TQ -->|
   SYNC  |       BS1        | BS2
   ───┬──┼──────────────────┼──────┬──
      │←→│←──────────────→│←───→│
        采样点（Sampling Point，典型 75%~80%）

    采样点为什么重要

    采样点 = 一位里「读取总线电平」的时刻。放太早，总线上信号还没稳定（传播延迟、线缆反射）；放太晚，留给 BS2 的余量不够。所有节点采样点应尽量一致（75% 左右），否则在长距离、高波特率下容易出现「这个节点读到了、那个节点没读到」的隐性不同步。这也是用 CAN 分析仪看波形时最常调的东西。

    同步机制：快慢钟对表的两把钥匙

    • 硬同步：每个帧起始 SOF 的下降沿强制触发，把总线沿对齐到 SYNC_SEG。每个帧都重新对表一次。
    • 重同步：帧中途遇到位沿与采样点偏差超过 SJW，把当前位缩短或拉长，最多调整 SJW 个 TQ（同步跳转宽度）。SJW 决定每个位能「掰」多大角度去追。
    重同步调整规则：沿落在 SYNC_SEG 之后 → 拉长 BS1（相位段1 延长，最多 SJW）
                沿落在 SYNC_SEG 之前 → 拉长 BS2（相位段2 延长，最多 SJW）

    晶振误差容忍度上限（F1 内部时钟 jitter 会吃掉余量）： 

    Δf ≤ SJW / (2 × 10 × NBT)      // NBT = 1 bit 的 TQ 数，粗略估算

    工程结论：BRP 让波特率分到合适的 TQ 数（8~25 TQ/bit），采样点设在 75% 附近，SJW 给 1~2，这是通用的稳定开局。F1/F4 的 bxCAN 采样点是通过 BS1、BS2 的「TQ 数量」间接定的（bxCAN 没有直接的采样点百分比寄存器），CubeMX 里直接给百分比，点开能看到对应的 BS1/BS2。

    五、配置说明：CubeMX + HAL

    CAN 的配置比 UART 多一层：除了波特率，还要配位时序、滤波器、中断、工作模式。下面以 F1/F4 的 bxCAN 为例。

    5.1 CubeMX 页面

    Connectivity → CAN1（F1 的 CAN 在 APB1 上，F4 的 CAN1/CAN2 也在 APB1），关键参数：

    参数 说明 典型值
    Bit Timings Parameters → Prescaler BRP 预分频，决定 TQ 时长 按波特率算
    Time Quanta in Bit Segment 1 BS1 的 TQ 数 13（配合下面示例）
    Time Quanta in Bit Segment 2 BS2 的 TQ 数 2
    ReSynchronization Jump Width SJW 的 TQ 数 1
    Auto Bus-Off Management 使能后硬件自动做 Bus-Off 恢复 强烈建议勾选（见第六节）
    Auto Retransmission 发送失败自动重发（硬件层面） 默认勾选
    Receive Fifo Locked Mode FIFO 满时新报文丢弃（保旧） 默认不勾
    Transmit Fifo Priority 多个待发报文谁先发：按 ID / 按 FIFO 顺序 按 ID

    勾选上方 NVIC Settings → CAN1 RX0 / RX1 / SCE 中断，生成代码才带收发中断回调。

    一个能跑通的配置实例（F4，APB1=42MHz，波特率 500kbps）： 

    APB1=42MHz，BRP=6 → TQ = 7 / 42M ≈ 166.7ns
1 bit = 16 TQ → 波特率 = 42M / (6+1) / 16 = 500kbps ✅
采样点 = (1 + 13) / 16 = 87.5%（BS1=13，BS2=2）  ← 略偏后，工程常用 80% 上下
    CubeMX 页面下方会实时显示 BiT Rate 和 Sample Point %，改 BRP/BS1/BS2 直接看，不用手算。

    5.2 滤波器（验收过滤）——接收方「挑食」的关键

    CAN 广播，每个报文所有人都收得到；滤波器的存在就是让节点只关心自己感兴趣的 ID，把 CPU 从无关中断里解放出来。F1/F4 有 14 个滤波器（F1 的 bxCAN），可配置为两种模式，都在 HAL_CAN_ConfigFilter() 里设置：

    模式 含义 适合场景
    掩码模式（Mask） 指定几位必须精确匹配、其余位「不关心」（掩码为 1 = 必须匹配，0 = 任意） 收一组连续/相关的 ID（如 0x100~0x10F）
    列表模式（List） 指定 ID 全部精确匹配，不匹配就拒收 只收少量固定 ID

    配置示例（掩码模式，收 0x123 一类）： 

    CAN_FilterTypeDef f;
f.FilterIdHigh         = 0x123 << 5;         /* 标准帧 11 位 ID 放高段 */
f.FilterIdLow          = 0x0000;             /* 扩展帧 ID / 低位过滤 */
f.FilterMaskIdHigh     = 0x7FF << 5;         /* 掩码：1 必须匹配 */
f.FilterMaskIdLow      = 0x0000;
f.FilterFIFOAssignment = CAN_RX_FIFO0;        /* 匹配的报文进 RX0 */
f.FilterActivation     = ENABLE;
HAL_CAN_ConfigFilter(&hcan, &f);

    5.3 初始化与启动（HAL）

    CAN_HandleTypeDef hcan1;

hcan1.Instance = CAN1;
hcan1.Init.Prescaler        = 6;    /* APB1=42M ÷7 → TQ≈166.7ns */
hcan1.Init.Mode             = CAN_MODE_NORMAL;
hcan1.Init.SyncJumpWidth    = CAN_SJW_1TQ;
hcan1.Init.TimeSeg1         = CAN_BS1_13TQ;
hcan1.Init.TimeSeg2         = CAN_BS2_2TQ;
hcan1.Init.TimeTriggeredMode    = DISABLE;
hcan1.Init.AutoBusOffManagement = ENABLE;   /* Bus-Off 硬件自动恢复 */
hcan1.Init.AutoWakeUp           = DISABLE;
hcan1.Init.AutoRetransmission   = ENABLE;
hcan1.Init.ReceiveFifoLocked    = DISABLE;
hcan1.Init.TransmitFifoPriority = DISABLE;  /* 0=按 ID，1=按 FIFO 顺序 */
HAL_CAN_Init(&hcan1);

    一个必须记住的启动顺序：HAL_CAN_Init → HAL_CAN_ConfigFilter → HAL_CAN_Start。漏掉最后一步 HAL_CAN_Start，HAL_CAN_Transmit/HAL_CAN_Receive 会一直返回超时错误（HAL_CAN_ERROR_...TIMEOUT），这是新手最常踩的坑。

    六、Bus-Off 快慢恢复：大事故后的自救

    当发送错误计数 TEC 累积到 ≥ 256，节点进入 Bus-Off：彻底退出总线，既不发送也不接收。这是 CAN 自我保护的最后一道闸——总线上有个节点一直报错，不把它踢下去，错误帧会把整条总线拖垮。但踢下去之后怎么回来，是「快恢复」和「慢恢复」之争。

    为什么有快慢两种恢复

    Bus-Off 恢复的本质是重新接入一条满负荷的总线，而这个节点自己对总线一无所知。关键差异在于它能否确定总线空闲：

    • 慢恢复（协议强制）：按 CAN 协议，Bus-Off 的节点必须连续观测到 128 次 11 个隐性位（即 128 × 帧间空间）才允许重新接入，过程中只做「倾听」，不做任何仲裁。这是标准做法，任何 CAN 控制器都支持，安全但慢（尤其在高负载下，要等很久才数满 128 个空闲间隙）。
    • 快恢复（bxCAN 的 Auto Bus-Off 模式）：bxCAN 在 AutoBusOffManagement=ENABLE 时，检测到总线空闲就立刻恢复发送，不等满 128 次，恢复更快，但对总线负载、电气环境的判断更激进——总线持续抖动时可能刚恢复又被踢下去。

    工程上怎么选

    场景 建议
    汽车级、安全关键总线（动力、车身） 慢恢复（协议强制）：规范第一，宁可慢、不冒险
    工业现场、调试期、负载不高的总线 快恢复（Auto Bus-Off）：恢复快，调试友好
    总线被干扰源持续破坏 快恢复反而会造成「踢了又回、回了又踢」的反复抖动，此时慢恢复更能保护总线

    实测观察：F4 的 bxCAN 勾选 Auto Bus-Off 后，Bus-Off 到恢复往往在毫秒级；不勾选则遵循协议 128 个隐性位，恢复时间与总线负载强相关。恢复后建议清一次应用层状态——比如节点重启通信状态机，或让上层协议补发离线期间丢失的报文。

    检测 Bus-Off 的寄存器

    F1/F4 在 CAN_ESR（错误状态寄存器）： 

    CAN1->ESR  & CAN_ESR_BOFF;   /* 1 = 处于 Bus-Off */
CAN1->ESR  & CAN_ESR_EPVF;   /* 1 = 错误被动 */
CAN1->ESR  & CAN_ESR_EWGF;   /* 1 = 错误警告（REC/TEC ≥ 96） */
CAN1->ESR  & CAN_ESR_TEC;    /* 发送错误计数（只读，可在此读状态） */
    HAL 侧则通过 SCE（状态改变）中断统一上报，见下节的 HAL_CAN_ErrorCallback。

    七、发送中断与接收中断：怎么让 CPU 不被数据拖死

    CAN 收发的量往往不小，轮询收发会把 CPU 耗在等 FIFO 上。中断化才是工程常态。F1/F4 的 bxCAN 有 3 个中断源（NVIC 里对应 3 个勾选框）：

    中断 触发时机 对应 HAL 回调
    CAN1 RX0 FIFO0 收到报文（每帧一次） HAL_CAN_RxFifo0MsgPendingCallback
    CAN1 RX1 FIFO1 收到报文 HAL_CAN_RxFifo1MsgPendingCallback
    CAN1 SCE（状态/错误中断） 错误状态变化、Bus-Off、唤醒等 HAL_CAN_ErrorCallback

    接收中断没有独立的「发送完成」中断位——发送完成也走 SCE（状态改变）中断，HAL 里由 HAL_CAN_TxMailbox0CompleteCallback 等回调区分。

    接收中断流程

    FIFO 满了会自动存到硬件 FIFO（每 FIFO 3 个邮箱）。接收侧 HAL 的机制是「中断通知 → 中断里取走」：

    /* 接收中断回调：收到一帧，立刻从硬件 FIFO 取到本地缓冲 */
void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan) {
    static CAN_RxHeaderTypeDef rxHeader;
    static uint8_t rxData[8];
    if (hcan->Instance == CAN1) {
        if (HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &rxHeader, rxData) == HAL_OK) {
            /* 取走成功：这里可以解析 ID、搬进应用队列，或置标志给主循环 */
            /* 注意：不要在中断里做耗时解析，搬完就走 */
        }
    }
}

    中断里的黄金法则：CAN 回调里只做「取出 + 搬运 + 置标志」，把数据丢给主循环或 RTOS 队列再处理。因为 FIFO 只有 3 个邮箱，回调里耗太久，新报文到达时 FIFO 溢出（HAL_CAN_ERROR_FOV0 溢出错误）——丢帧不是 CAN 的错，是中断没及时取走。

    发送中断流程

    发送侧分两步：请求发送 → 等待完成回调。HAL 用 3 个发送邮箱（Mailbox）并行管理，每封邮件独立回调：

    /* 1. 发送请求（中断模式下发出后立即返回，不阻塞） */
uint8_t txData[8] = {1,2,3,4,5,6,7,8};
CAN_TxHeaderTypeDef txHeader;
txHeader.DLC      = 8;                     /* 数据长度 */
txHeader.IDE      = CAN_ID_STD;            /* 标准帧 */
txHeader.RTR      = CAN_RTR_DATA;          /* 数据帧 */
txHeader.StdId    = 0x123;
txHeader.TransmitGlobalTime = DISABLE;

uint32_t mailbox;
HAL_CAN_AddTxMessage(&hcan1, &txHeader, txData, &mailbox);

/* 2. 发送完成回调：这帧真发出去了（或被硬件重发后成功） */
void HAL_CAN_TxMailbox0CompleteCallback(CAN_HandleTypeDef *hcan) {
    /* 0 号邮箱完成：可以在这里释放对应报文资源 / 记录已发送 */
}

    发送中断 vs 轮询，什么时候用哪个

    方式 特点 场景
    HAL_CAN_Transmit（轮询） 阻塞，等待发出或超时 初始化自检、低频发送
    HAL_CAN_Transmit_IT（中断） 立即返回，完成后回调 日常发送，推荐
    HAL_CAN_Transmit_DMA 数据走 DMA，进一步减 CPU 负担 大包数据、高频周期性发送

    高频周期发送的工程惯例：主循环或 RTOS 任务里调用 HAL_CAN_AddTxMessage 填邮箱（邮箱空时立刻成功返回），发送完成在回调里收尾——不要在发送完成回调里再发下一帧（回调里做发送在 HAL 的某些时序下会重入异常）。

    错误与状态回调：把「总线的病」报给应用

    HAL_CAN_ErrorCallback 接收所有状态类变化，是排查 CAN 异常的入口：

    void HAL_CAN_ErrorCallback(CAN_HandleTypeDef *hcan) {
    uint32_t err = HAL_CAN_GetError(hcan);
    if (err & HAL_CAN_ERROR_ACK)        /* ACK 错误：总线上没别的节点响应 */
        ; /* 检查是否只有本节点在线上、终端电阻是否匹配 */
    if (err & HAL_CAN_ERROR_CRC)        /* CRC 错误 */
        ;
    if (err & HAL_CAN_ERROR_FOV0)       /* FIFO0 溢出：接收太慢，回调里处理太久 */
        ;
    if (err & HAL_CAN_ERROR_BOFF)       /* Bus-Off：触发过 Bus-Off */
        ; /* 恢复前应用层做状态重置 */
}

    最常见的两个 HAL 错误，直接对应前面讲的内容： - HAL_CAN_ERROR_ACK（ACK 超时） → 总线上只有自己，或对端没在听。测试时只要接 USB-CAN 分析仪就能消除，确认「有人收到」。 - HAL_CAN_ERROR_FOV0（FIFO0 溢出） → 接收回调处理太慢，把 3 个邮箱挤爆了。

    八、避坑备忘

    • 波特率算错一整条：改 APB1 时钟后，BRP/BS1/BS2 一定要重新核对——TQ 是跟着 APB1 走的。CubeMX 页面右下角直接显示最终波特率。
    • 漏调滤波器的模式：掩码模式 FilterMaskIdHigh=0 会把所有报文都放进来（全不关心），看起来「收得到」但 CPU 被无关中断打满——要么配好掩码，要么用列表模式。
    • 终端电阻不是「多接无害」：标准是两端各 120Ω，接多了会拉低总线阻抗、缩短有效长度；一个都不接，波形反射严重。调试箱接一个 USB-CAN 分析仪时它常自带 120Ω，注意别和板端重复。
    • Bus-Off 后「卡死」的假象：没有使能 Auto Bus-Off 时，节点可能在 TEC=256 后长时间处于 Bus-Off，应用以为「死了」，其实是在数 128 个隐性位等总线空闲。
    • 中断里千万别做重活：接收回调里做 CRC 校验、进协议栈、打印日志，都是把 FIFO 挤出溢出的行为。取走数据、置标志、交给主循环/队列，完事。
    • ST 的 F1/F4 有且只有 2 个 CAN：CAN1 是主，CAN2 的过滤器共用 CAN1（CAN2 的滤波器配置要挂在 CAN1 的滤波器组上，且 CAN2 的启动依赖 CAN1 的时钟）。用到 CAN2 时，务必先配好 CAN1。
